# 内容包装与优化

> 目标：把同一份真实经历压缩成目标岗位能快速识别、愿意继续核验的表达。
>
> 包装不是改事实，而是选择事实、重命名事实、调整颗粒度和控制披露顺序。允许省略无关信息，不允许虚构项目、职责、结果或任职时间。

## 先确定包装要解决什么

先问：目标岗位的筛选者最担心什么、最想看到什么证据？

包装服务于三个判断：

- **相关性**：这段经历和目标岗位有什么关系？
- **可信度**：候选人在其中做了什么，是否有结果和证据？
- **可迁移性**：没有完全相同的 title 或行业经验时，哪些能力可以迁移？

如果一句话只让人觉得“态度不错”或“愿意学习”，却无法对应具体任务、决策或产物，它通常不是有效包装。

## 四类可用的包装

### 1. 选择与省略

围绕目标岗位选择相关事实，省略无关细节。省略不是隐瞒硬性事实；时间、学历、任职关系、项目和结果不能被删除后造成错误理解。

可用：

- 同一项目中，产品岗突出问题定义、取舍和交付；开发岗突出架构、实现、稳定性和结果。
- 早期杂项经历与目标无关时，可以不占主叙事位置。

不可用：

- 删除关键的负面事实后，使剩余内容产生相反结论。
- 把团队成果全部改写成个人成果。

### 2. 语义翻译

把内部 title、流程名和工具名翻译成招聘方熟悉的说法，但保留真实职责边界。

包装顺序：

1. 事实：实际做了什么。
2. 可识别名称：招聘方怎么称呼这类工作。
3. 一个关键动作：怎么做的。
4. 一个结果或产物：最后交付了什么。

以 AI 产品与开发方向为例：

| 原始事实 | 面向 AI 产品岗 | 面向 AI 应用开发岗 | 面向全栈岗 |
|------|------------------|----------------------|------------|
| 跟进企业 AI 项目 | 业务场景判断、产品定义、跨团队交付 | LLM 应用方案、接口与工作流落地 | 前后端与部署的端到端交付 |
| 研究模型和成本 | 模型/算力选型与成本取舍 | 推理方案、延迟与稳定性优化 | 技术选型、资源评估与工程权衡 |
| 把重复工作做成工具 | AI 原生工作流与产品化能力 | Agent/Workflow/Skill 工程化 | 自动化、CI/CD 与研发效能 |

同一个事实只能有一个主归属模块；其他模块不重复展开。

### 3. 颗粒度对齐

从目标 JD 中提取筛选者使用的动词和对象，把经历改写到同一颗粒度：

- 岗位要求“产品规划”时，写清目标用户、范围、优先级和版本。
- 要求“需求分析”时，写清业务问题、约束和方案取舍。
- 要求“落地交付”时，写清跨职能范围、里程碑和结果。
- 要求“Agent/RAG”时，写清任务链路、工具边界、数据流和失败处理。

不要把“参与需求沟通”包装成“主导产品战略”，也不要把“做过 API 调用”包装成“负责模型平台架构”。

### 4. 程度与时间压缩

程度词和时间范围可以按招聘语境压缩，但必须与下方事实和时间线兼容。

#### 能力程度

| 实际证据 | 可写程度 | 不建议 |
|------|----------|--------|
| 读过资料、跑过 Demo、少量使用 | 了解 / 有实践 | 熟练、精通 |
| 在多个任务中使用，能独立完成常规工作 | 熟悉 | 精通 |
| 在真实项目中独立交付，能解释选型、边界和异常处理 | 熟练应用 | 只写“用过”而埋没能力 |
| 深入机制、能架构、排障、处理边界，并能指导他人 | 精通（慎用） | 仅凭短期使用写精通 |

“用过写精通”能否成立，取决于“用”的深度和次数，而不是措辞技巧。不能为满足 JD 关键词越过证据等级。

#### 经验时间

- 简历里的任职日期保持真实。
- 标题可使用“1 年+”“近 2 年”等概括，但必须与可见时间线兼容。
- 若经历区间本身只支持一年半，标题写“两年经验”容易被时间线直接证伪；更稳妥的是“近两年相关实践”或“1 年+ 正式经验”，并说明是否合并了实习、开源或个人项目。
- 不得把实习、兼职、个人项目不加区分地合并成正式工作经验。

## 课程、论文与 Blog 的包装

学习证据不是技能列表本身。先判断它证明了什么，再决定放在哪里：

| 证据 | 能证明 | 简历写法 |
|------|--------|----------|
| 课程 | 系统基础知识、跟随权威机构学习 | 只保留讲师/机构 + 主题，不写完整课程清单 |
| 论文 | 对模型机制、工程路径或评测方法的理解 | 只保留团队/作者与主题，不堆论文标题 |
| 技术 Blog | 跟踪工程实践和一手经验 | 写持续阅读的团队/领域，不写篇数 |

示例结构，不直接套用：

> AI 技术理解：系统学习某机构的大模型、Agent 与后训练课程；持续阅读某团队关于 Agent 工程、工具调用与长时任务的论文和 Blog，并将相关方法用于项目方案与工作流设计。

完整课程、论文、Blog 链接放作品集或材料池；简历只保留能帮助目标岗位判断的一行证据。

## 工具和技能写法

- “能力描述”回答你擅长什么；“技能”还要能看出对象、方法、工具或边界。
- 工具名只在真实使用且与岗位相关时出现。
- JD 明确要求 Figma、Axure、墨刀等工具时，只有候选人确实使用过才写；否则用“原型与交互设计”描述能力，不硬凑工具关键词。
- 不写纯名词堆砌。优先用“方法/工具 + 解决什么问题 + 可验证结果”。
- 工作流 Skill、自动化脚本和自研工具属于交付能力；不要把 10 个工具名逐项塞进技能区。

## 学习能力怎么写

“学习能力强”不能作为结论单独出现。用行为链证明：

> 学了什么 → 用在哪里 → 产出什么 → 形成什么判断

例如：

- 不是“自学能力强”，而是“持续学习 Agent 工程课程与论文，并将方法用于工作流和 Bad Case 设计”。
- 不是“拥抱 AI”，而是“默认用 AI 完成调研、原型、编码与验证，并把重复流程沉淀为可复用 Skill”。

## 事实边界

包装前给每项高风险表述做一次追问：

1. 面试官追问细节时，我能否说出真实任务、角色和结果？
2. 时间线、项目文档或作品链接是否与这句话冲突？
3. 我把团队成果归给个人，还是把个人贡献写成了团队成果？
4. “熟练/精通/主导/负责/从 0 到 1”是否有足够证据？
5. 如果对方要求现场演示或解释，我能否完成？

任一答案是否定，就降低程度、缩小范围或删掉。

## 交付前自检

- 每个强结论能否落到一条具体证据？
- 是否把目标岗位需要的经历放到了更容易找到的位置？
- 是否只改了名称和顺序，还是增加了不存在的事实？
- 程度词是否对应当前能力判据？
- 经验年限是否与经历日期自洽？
- 学习证据是否压缩到一行，详细来源是否放到作品集？
- 工具关键词是否真实使用过，而不是为了 ATS 拼凑？
