# 项目讨论（简历层）

写简历和改简历都需要挖掘项目经历。本文件定义**简历层**的项目讨论流程：怎么和用户聊项目、怎么把素材整理到 materials.md、怎么从素材生成简历 bullet。

> **素材获取与原始文件落盘的物理流程**（markitdown 转换、归档到 `_shared/files/`）属于 **amlei-profile** skill 的职责，见它的 `references/ingestion.md`。本文件只讲简历层的讨论逻辑。

## 项目类型

| 类型 | 说明 | 讨论切入点 |
|------|------|-----------|
| **公司项目** | 在职期间参与的工作项目 | 优先让用户给相关文档/材料；没有就跟用户聊。属于某 experience 下 |
| **个人项目** | 业余自建、个人作品 | 优先看作品链接/作品集；没有就跟用户聊。属于 `exp_standalone` |

## 探索式梳理（基于已有素材）

进入讨论前，amlei-profile 已完成素材提取（原始文件已落盘 `_shared/files/`，事实层 `_shared/experiences.json` 已有项目条目和多粒度描述）。本层的工作：

1. **读 `_shared/experiences.json`** 拿到当前事实层里这个项目已有的 granularity 描述
2. **像接手陌生系统一样**深入理解整条链路：背景、上下游、用户角色、量化指标
3. 把**简历层的理解**（讨论沉淀、framing 想法）写入本次任务的 `materials.md`，**不**写回事实层（事实层归 amlei-profile 维护）

### 带推理读素材 → 待问疑点

用户给的材料往往比他自述的更多。带着"他还做过什么没说"的眼光去读：

- **没明说的职责**：协作记录里别人的任务是你建的 → 你是不是还做了协调？
- **时间转折 / 空白**：不同时期领域、技术栈、岗位发生变化 → 问怎么过渡
- **规模 / 协作范围**：经手的量级、对接人数，往往暗示比"执行者"更大的职责
- **任何没看明白、想确认的细节**

把这些疑点记入 `materials.md` 的「待问疑点」区，留到[讨论补充](write-revise.md)环节问用户。

### 讨论挖掘（无材料时）

如果用户没材料，跟用户聊：

1. **项目背景**：这个项目做什么？解决了什么问题？
2. **你的角色**：你负责了什么？主导、核心参与还是协助？
3. **方法/过程**：用了什么方法或工具？为什么选它？
4. **难点与解决**：最大的困难是什么？怎么解决的？
5. **量化成果**：带来什么可量化结果？（效率提升、用户增长、收入提升、覆盖率等）

## 素材结构（任务局部）

讨论/挖掘的结果保存到本次简历目录：

```
identities/{identity-id}/resumes/{app-id}/
├── 简历.md
├── _meta.json
├── jd.md
├── materials.md          # 本次简历任务的项目讨论 / framing 想法
└── files/                # （可选）本次任务相关的额外文件
```

`materials.md` 是**任务局部**——它不属于事实层（事实层在 `_shared/`），是本次写简历时的 brainstorm 记录。下次改简历可以参考，但真相源是 amlei-profile 的事实层。

## 回写事实层（重要！）

讨论中如果挖到**新的客观事实**（用户之前没记的能力、之前没记的项目、修正的数字），必须经评估 + 用户确认后回写到 `_shared/`（调用 amlei-profile 的流程）。

**只写进 materials.md 不算数**——下次会话你只会读 amlei-profile 的事实层，materials.md 是任务局部的。

## 迭代更新

`materials.md` 不是写一次定稿。讨论中素材逐步清晰——用户补充细节、纠正说法、给出量化数字——都应更新到对应条目。
