# 写/改简历

从零写或迭代改写目标岗位简历。写和改本质相同——都是基于用户资料和岗位市场信息，对简历内容的改写操作。

## 收集就业市场信息

以 subagent 方式调用 amlei-job-market-research skill（输入：求职岗位 + 目标城市），产出市场报告（薪资、能力要求、行业趋势等），写入 `identities/{identity-id}/resumes/{app-id}/research/市场报告.md`，作为后续简历定位与改写的依据。

## 分析用户项目资料

以 subagent 方式分析用户提供的项目资料（项目地址、项目文件），拆解用户做过什么、成果是什么。分析报告写入 `identities/{identity-id}/resumes/{app-id}/research/分析.md`。

**⏸️ 人工确认**：展示分析报告，由用户确认准确性。用户指出遗漏或误读时，补充修正后再次确认。

**回写 amlei-profile 事实层（强制，最易遗漏）**：分析中挖到的**真实客观事实**（新能力 claim + 证据、新项目、修正的 metric），不能只写进 `分析.md` / `materials.md` 就交差——那两份是任务局部的。必须按 amlei-profile 的 [fact-evaluator.md](../../amlei-profile/references/fact-evaluator.md) 流程，经评估 agent + 用户确认后回写到 `_shared/`（事实层），否则这些发现随任务结束而丢失。

注意区分：客观事实 → amlei-profile；framing（怎么讲、bullet 措辞）→ 本 skill 的 emphasis。详见 amlei-profile SKILL.md 的"事实 vs 强调判别"。

## 讨论补充（Human-in-loop）

分析确认后，进入持续讨论环节——围绕"用户在这份简历想呈现怎样的自己"。这一环节的核心不是等用户说，而是**主动追问**：用户记忆是碎片化的，聊到一半才想起来的事，你不问就永远沉没。

**三类必问：**

1. **把分析阶段的「待问疑点」逐条抛出**：[projects.md](projects.md) 带推理读材料时记下的疑点（角色越界、时间转折、规模暗示等），逐条直接问用户——"我看 XX 是你做的，你是不是还负责了 YY？"。这些疑点最易挖出隐性经历，不要放过。
2. **主动问"还做过什么"，从该领域的周边职能给角度**：别只笼统问"还有吗"（用户多半答不上）。结合目标岗位所在领域，把常被遗忘的周边职能逐个确认（**以下仅是举例，按实际领域替换**）：
   - 技术类周边：任务分配 / 排期、客户或需求对接、UI / 原型设计、跨部门协调、文档 / 带教
   - 其他领域类比：运营的跨部门 / 活动 / 数据分析、产品的竞品 / 需求走查、设计的规范 / 走查……
   - 关键是**给用户具体的钩子去回忆**，而不是开放空问。
3. **聊到新东西就即时落盘**：讨论中冒出的新能力 / 项目 / 成果（哪怕零碎），**当场写进 `materials.md`**——这是本次任务的发现记录，后续改写简历直接从这里取材；不写下来容易忘，挖到的就白挖了。值得跨岗位复用的，再评估 + 确认后写回 profile（个人能力记忆）。别攒到最后。

这三类追问**贯穿整个讨论，不是问一次就完**。每聊完一段经历，都再问一遍"这段之外还搭手做过什么吗"。

详见 [projects.md](projects.md)。

## 写作规则

### 全局核心原则

1. **去标签化与去括号化**：严禁纯名词标签（如 `Java | MySQL | Docker`）；严禁技能描述中大量使用长括号做名词解释——静态名词必须转化为动态能力描述（动词 + 场景 + 结果）。
2. **数据量化**：价值描述尽可能含量化数据（百分比/时间/金额/并发量/用户数）；无精确数据用合理估算量级（万级/秒级），不得虚构精确数字。
3. **动词开头**：职责与业绩以强行为动词开头（主导、设计、重构、优化、落地、拉通、驱动）。
4. **STAR-L**：项目经验体现情境/任务/行动/结果，并额外强调 Learning / Trade-off（技术权衡与思考）。
5. **真实性与克制**：严禁编造经历；谨慎使用"精通"，除非有底层源码级或架构级深度证明；优先"深入掌握""熟练掌握""熟悉"。

### 通用规范

**脱敏**：简历经历中涉及公司内部项目名称，一律用业务功能描述或规模定义替代（如"核心交易链路"、"支撑日均百万订单的订单系统"），严禁写入公司项目原文名称。不用"某"式占位表述。

**平实表述**：每句话让读者一眼看明白你具体做了什么。写每条经历时主动问用户"你当时具体是怎么做的"，引导他说出执行细节再落笔，不替用户编造。**不解释领域常识**：标准技术名词和概念（如"Skill""YAML frontmatter""Context Engineering"）是读者已知的领域常识，不在简历中解释它是什么。要么删掉无差异化的技术列举，要么只写你做了什么/做成了什么，不写"XX是什么"。

**链接限制**：仅 `self-intro` 模块可含外部链接（GitHub/作品集等），其他模块禁止出现链接。

### 漏斗逻辑（模块分工，写前先想）

简历是漏斗形的说服工具，每个模块只承担自己的说服功能，不越界——个人简介**定调**（电梯演讲，建立人设吸引往下看）→ 技能块**秀肌肉**（证明人设有硬核技术底座）→ 工作经历**验背景**（证明在真实商业环境打过胜仗、懂业务能落地）→ 项目经历**抠细节**（回放关键战役的微操，展示技术深度与填坑能力）。落笔前先过上方「全局核心原则」。

### 模块编写规范

模块格式硬规则见 SKILL.md「简历格式」表；模块顺序 = MD 里 `#` 出现顺序。

#### self-intro（头部）

头部模块——name / role / 联系方式 / avatar / links + education（教育背景作缩进子项），渲染成 Header。`name:` 必填；`avatar:` 给照片相对路径；`links` 放可线上展示自己的链接。

#### 个人简介（定调 · 电梯演讲）

独立 `# 个人简介` 模块，下接一段纯文本（渲染成 Summary）。不要把个人简介塞进 self-intro 当尾部文字——Header 里 trailing 段落会渲染异常。

- **定位是电梯演讲**：3-4 句高度概括核心竞争力。双视角检验——HR 读到「背景达标、方向对口、表达清晰」（心理活动：推给技术部门）；面试官读到「有底层探究精神、懂业务闭环」（心理活动：不是只会写 CRUD 的螺丝钉，值得聊聊）。
- **三段式黄金公式**：【核心定位与年限】+【技术壁垒/高光成果】+【业务 Sense/软性特质】。
- **三条禁区**：不写兴趣爱好流水账、不写性格自评（吃苦耐劳/性格开朗）、不写假大空口号（致力于用 AI 改变世界）；爱好仅在可量化且与岗位相关时保留（如技术内容输出的阅读量数据）。
- **通用模板**（占位符按真实情况填写，禁止照抄他人领域名词）：
  > 具备 [X] 年 [核心领域，如：后端开发/数据分析/产品设计] 经验，专注于 [核心细分方向，如：高并发架构/数据驱动增长]。具备极强的底层探究与问题解决能力，曾 [一句话概括最亮眼成果，如：主导核心系统重构，使吞吐量提升 50%]。不仅关注技术深度，更具备端到端的业务交付能力，擅长在复杂业务场景下通过 [某项核心能力] 实现降本增效。

#### 工作/实习经历（验背景 · 岗位纵览）

一家公司一个条目，保持"面"的完整。

- **本质是岗位纵览，不是职责清单**：回答"这个人在这个岗位上是怎么干活的"，不回答"负责了哪几件事"。用**工作闭环**呈现做事路径——以某领域为例：「接到业务问题 → 调研可落地的方案 → 选型论证 → 落地实现 → 沉淀为可复用流程/工具 → 推进项目与客户」，让读者看到从接事到交付的完整过程。
- **两条反面红线**：① 不写"负责 A、负责 B"式职责标签罗列——读起来像"只做了这些"，信息量为零；② 不把具体业务项目的细节与数字堆进工作经历——那是 `# 项目经历` 的活，工作经历只保留能力级量化（规模、协作人数、交付范围）。
- **结构**：一句**业务背景**（先给业务的规模/复杂度，如"负责核心 AI 智能客服与 Agent 调度平台，日均处理千万级对话请求"）+ 一句岗位总述（如"负责某领域应用从 X 到 Y 的端到端交付"）+ 2-4 条工作闭环 bullet（每条 = 动作 + 判断 + 落地，**动词开头、数据收尾**）。业务背景句是给 HR 的——判断业务线是否核心；给面试官的——判断问题复杂度。
- **区分职责与业绩**：职责是"你该干嘛"，业绩是"你干成了什么样"——bullet 优先写成业绩句；纯职责内容并入岗位总述，不单独成条。
- **高光时刻**：可在条目内嵌入 1-2 条带量化的突出成果，回答"在这家公司干成了什么"。基本盘与高光时刻在同一条目内，不拆成独立项目。
- **编写公式**：`[公司/部门/职位/时间]` → `[业务背景(一句话)]` → `[核心职责(2-3 条)]` → `[核心业绩(2-3 条，数据化)]`。
- **双视角校验**：HR——公司背景、在职时长、职级是否合理且稳定？面试官——负责的业务是核心还是边缘？产出对业务的实际影响是什么？
- **通用模板**（职责条目须写成工作闭环/业绩句，不做职责标签罗列）：
  > **[公司名称] | [部门名称] | [职位名称] | [YYYY.MM - YYYY.MM]**
  > **业务背景**：负责 [核心产品/系统名称] 的研发与迭代，支撑 [业务规模，如：日均百万级请求/千万级营收]。
  > **核心职责**：主导/参与 [核心模块] 的架构设计与开发，负责 [具体技术/业务链路] 的攻坚；拉通 [跨部门角色]，推动项目从需求拆解到交付的全生命周期管理。
  > **核心业绩**：**架构/流程优化**——重构 [某系统/流程]，引入 [某技术/方案]，使 [核心指标] 提升 [X]%；**业务/性能突破**——解决 [某棘手问题]，使 [QPS/转化率] 提升 [X]%，P99 延迟降低 [Y]%。

#### 项目经历（抠细节 · 深水区）

满足 4 条件才单列：起止时间明确 + 可量化目标 + 核心角色 + 完整闭环结果。分公司项目和个人项目，**公司项目在前，个人项目放后**，让工作经历和项目之间形成自然衔接感。

- **与工作经历的分工**：工作经历回答"怎么干活"（纵览），项目经历回答"干成了什么"（证据）——同一件事只在项目经历展开细节，不在工作经历复述。
- **进阶 STAR-L**：每条 bullet 呈现「**技术挑战 → 解决方案（我的贡献）→ 结果（量化）**」——显式写出核心技术难点，这是吸引面试官深挖的"诱饵"；方案句写**关键决策与权衡**（Trade-off：在资源/时间/性能之间为什么这么选），不落到配置与实现细节（与"写做到什么不写怎么做到的"一致）。结果必须量化（如「单次任务 Token 消耗减少 40%」「问答准确率 65% → 88%」）。
- **编写公式**：`[项目名称/角色/时间]` → `[项目描述(极简 1 句)]` → `[核心技术/业务挑战]` → `[解决方案(我的贡献 + 权衡)]` → `[项目收益]`。
- **双视角校验**：HR——项目规模是否足够？是否包含目标岗位关键技术栈？面试官——为什么选 A 不选 B？最大的坑是什么？如何排查解决？
- **通用模板**（占位符按真实事实填写）：
  > **挑战：[具体痛点，如：长链路导致响应延迟高 / 复杂场景下数据准确率低 / 多模块并发时状态混乱]**。
  > **解决**：设计并落地 [具体方案]，在 [某环节] 引入 [某技术/算法]；在 [技术选型] 上权衡了 [方案 A] 与 [方案 B]，最终选择 [某方案] 以兼顾 [性能/成本/开发效率]。
  > **收益**：在保证 [底线指标] 的前提下，使 [核心指标] 优化 [X]%，彻底解决 [某痛点]。

#### 技能（秀肌肉 · 能力底座）

`类别: …` 每类一行；行格式细则以 SKILL.md「简历格式」表为准，此处是内容方法论。

- **双视角校验**：HR——是否覆盖 JD 核心关键词？面试官——是停留在"会用 API"，还是懂"底层原理与调优"？
- **写流畅能力句，禁纯标签与括号地狱**：三档递进——纯标签（`Python · SQL · Linux`）是名词堆砌；标签+程度词（`精通 Python`）有层次但单薄；标准是**完整能力句**：`程度词 + 核心技术 + 具体能力/动作 + 深度/结果`，如「熟练掌握多智能体编排与上下文工程，能够独立实现子 Agent 调度与工具并发调用，并落地上下文自压缩以降低 Token 消耗」。
- **程度词诚实且有策略**：四级判据以 amlei-profile SKILL.md R1 为唯一源（精通=懂底层原理/能解疑难/能造轮子，**慎用**——写了就会被往底层和源码追问；熟练=日常主力技术、独立高效交付复杂业务；熟悉=项目用过、能完成日常开发；了解=概念/Demo 级）。面试官按程度词调整提问深度，必须实事求是；多数技能落「熟练 / 熟悉」更可信，满篇"精通"是减分项。
- **括号克制，防"词典化"**：括号会打断视觉流，两三个长括号就让 HR 工作记忆超载——整行至多一处轻量补充（分数/版本号类），单句超 40 字或 2 个括号必须拆句重写。拆法：①括号里的名词提取出来加动词与业务场景，变「动作+场景」短句；②琐碎细节抽象为「从 Embedding 选型到业务落地的全流程实战经验」式概括，细节留给面试口述或项目 bullet；③高光亮点单独成句重笔墨（如「具备底层探究能力，深读 Claude Code 源码并以 Rust/TS 独立复刻 Agent 内核」），不与常规技能挤一句。禁止"了解 XX 协议 / 了解 XX 思想"式空话——要么落到具体应用，要么删。
- **三写三不写**：写能力边界不写操作手册（参数配置/实现细节留给项目经验）；写业务价值不写纯技术名词（「上下文自压缩以降低 Token 成本」「显存精准测算以保障推理稳定性」）；写流畅短句不写带括号的长句。
- **核心前置**：类内把最拿手、与 JD 最相关的技能放最前（读者视线集中在每行开头）；类别顺序同理，目标岗位的主力技能类放模块最前。
- **对齐 JD**：逐条对照 JD，反复出现的核心技能关键词必须出现在技能区——哪怕自评只有"熟练"也如实写出，好过笼统不写；JD 没提的技能靠后或删。
- **等级可举证**：技能区每一项都应能指向某条经历 / 项目 bullet 作为证据（呼应事实层 `proven_by`）——**没在项目里用过的技术不写**；举不出证据的高等级降级或删，工具类名词按"能力不写工具"规则移到项目里。
- **等级取自事实层**：程度词优先读 `_shared/capabilities.json` 的 `proficiency`（跨简历、跨会话保持一致）；该能力未定级时与用户商定，**确认后回写事实层**（走 amlei-profile 的评估 + 确认流程），不要每份简历各自现拍。方向括号不入事实层，按岗位从证据组装。
- **软技能 / 业务 sense（可选）**：高级岗位可在最后加一条业务抽象、跨团队协作、带教 / 评审类能力，只写有经历支撑的。

## 共创/迭代改写

默认逐节共创：按 个人简介 → 经历 → 技能 顺序，每节基于挖到的素材 + 市场报告出一版给用户确认 / 改，再下一节。要快就切「先整篇草稿再改」。

改已有简历时同理——看到已有 bullet，追问"这个项目你具体负责了什么"、"有没有遇到意外情况"、"结果能用数字说明吗"，帮用户把已有经历写得更具体、更量化。聊完一段经历后问"还有没有类似的项目"、"实习之前还做过什么相关的吗"，找出沉默亮点。

经历用 STAR + 量化，只放与岗位相关的；个人资料里的项目地址优先访问核实数据。

## 用户确认后再保存

每版内容经用户明确认可后，再写到 `identities/{identity-id}/resumes/{app-id}/简历.md`。用户没说"可以/就这样"之前，绝不写入。

保存时同步写 `_meta.json`（见 [snapshot-fork.md](snapshot-fork.md)）：`source_operation` 标 `new_from_emphasis`（已有身份下首份）或 `fork`（基于旧版改）；`facts_version_at_creation` 取当前 `_shared/_meta.facts_version`；`delivered: false`（投出时再翻 true）。
