# 作品集格式与写作规范

本文件定义 `amlei-portfolio` 的单文件结构、案例写法和素材规则。作品集有独立 Skill 入口与 reference 契约，运行数据归属于简历数据根下的 `portfolio/`。

## 1. 先确定作品集要完成的判断

作品集通常服务于初筛之后的深入阅读。以下是常见浏览者，不是固定分类：

| 浏览者 | 主要判断 |
|--------|----------|
| HR / 招聘方 | 方向是否匹配、案例是否真实、是否值得继续联系 |
| 业务面试官 | 是否理解用户与业务、能否定义产品、能否做取舍 |
| 技术 / 交付面试官 | 是否理解系统边界、数据与异常路径、能否推进落地 |

写之前先回答：

1. 这个作品集给谁看？
2. 阅读者需要补充哪些简历无法证明的判断？
3. 哪些案例最能提供这些证据？
4. 哪些内容必须公开、脱敏或不展示？

## 2. 选择 2-5 个主案例

每个主案例承担一个主要证明任务。常见组合：

- 一个完整解决复杂业务问题的案例；
- 一个从 0 到 1 或独立交付的产品；
- 一个体现专业判断、技术或数据取舍的案例；
- 一个体现用户研究、体验设计或内容表达的案例。

优先选择与目标岗位直接相关、有问题与结果、有可核验证据、能支撑面试追问的案例。

不要把只有功能清单、重复证明同一种能力、无法说明个人贡献或公开边界的项目放进主案例。

## 3. 单文件结构

默认路径：

```text
.amlei-skill/resume/portfolio/
├── {identity-id}-作品集.md
└── assets/
    ├── images/
    ├── videos/
    ├── documents/
    └── diagrams/
```

`{identity-id}-作品集.md` 是该方向的唯一内容源，包含：

- 定位与公开联系方式；
- 案例选择与排序；
- 每个项目的问题、角色、关键判断、交付、结果、证据和边界；
- 项目状态与公开范围；
- 发布地址和最近更新时间。

不建立 `profile.md`、`projects/`、`target.json`、`_meta.json`、`review/`、`archive/`、`export/` 或独立发布记录。多个方向需要并行时，在同一目录下增加 `{identity-id}-作品集.md`，并共用 `assets/`。

## 4. 作品集元信息

文件顶部可使用 YAML frontmatter 保存不会直接展示的发布信息：

```markdown
---
title: "{姓名} · {方向}作品集"
direction: "{方向}"
updated_at: "{YYYY-MM-DD}"
published_url: "{线上链接；未发布时留空}"
---
```

不要为这些字段另建 JSON 或发布记录文件。

## 5. 作品集正文

正文使用标准 Markdown：

```markdown
# {姓名} · {方向}作品集

> {一句话说明目标方向、解决的问题和主要证据}

## 快捷链接

- 简历：
- GitHub：
- 个人网站：

## 精选案例

| 案例 | 主要证明 | 证据 |
|---|---|---|
| {项目名} | {能力或判断} | [体验 / 视频 / 源码]({url}) |

## {项目名} | {项目类型} | {角色}

| 时间 | 状态 | 公开范围 |
|---|---|---|
| {时间} | {状态} | {public / desensitized} |

- 产品体验：[{url}]({url})
- 演示视频：[{url}]({url})
- 源码：[{url}]({url})

{为谁解决什么问题，为什么值得解决。}

### 关键判断

- {选择与放弃}
- {产品、技术、成本、体验或交付上的取舍}
- {异常、风险或人工边界}

### 产品与交付

{核心流程、关键体验、系统边界和最终产物}

### 结果与证据

- {结果或验证结论}
- {图片 / 视频 / Demo 应重点看什么}

### 边界与反思

{未完成项、样本限制、下一步验证}

## 其他作品

- {名称}：{问题与价值} · [链接]({url})

## 关于我

{与目标方向相关的工作方式、专业训练和持续实践}

## 联系方式

{按公开边界填写}
```

不宜使用平台专有的 XML、内部媒体 Token 或无法迁移的嵌入语法。导入外部平台时由对应工具适配。

## 6. 单个案例的七项证据

每个主案例至少回答：

1. **问题**：谁遇到了什么问题，为什么值得解决？
2. **角色**：本人独立负责、核心参与还是协作支持？
3. **判断**：做了哪些关键选择，放弃了什么？
4. **交付**：形成了什么产品、系统、流程或原型？
5. **结果**：有什么结果，处于哪个验证阶段？
6. **证据**：在哪里可以体验、观看、阅读代码或看到反馈？
7. **边界**：还有什么未解决，哪些结果不能归因于本人？

任何一项长期缺失，都应缩短该项目或移除主案例位置。

## 7. 素材目录与命名

图片、视频、文档和图表放在：

```text
assets/
├── images/
├── videos/
├── documents/
└── diagrams/
```

命名：

```text
{project-id}-{english-purpose}.{ext}

示例：
project-a-overview.webp
project-a-user-flow.png
project-b-demo.mp4
project-b-system-map.svg
```

规则：

- 文件名使用英文小写 kebab-case，项目 ID 保持稳定；
- Markdown 使用相对路径，例如 `assets/images/project-a-overview.webp`；
- 外部已有稳定 URL 时优先外链，不复制；
- 大型视频优先使用稳定外部 URL；
- 图片必须有可见内容说明，视频必须标明时长和重点片段；
- 公开版本不得包含客户名称、内部系统、账号、真实业务数据或未脱敏截图；
- 素材内容变化时保留新版本，不静默覆盖已发布版本。

## 8. 状态与公开范围

项目状态：

- `已发布`：外部用户可获得并使用；
- `内部上线`：已在组织内部使用，但未公开发布；
- `Pilot`：真实用户小范围验证；
- `原型`：有可交互产物，未进入正式交付；
- `已归档`：停止维护，保留作为历史案例。

公开范围：

- `public`：可直接公开；
- `desensitized`：经过脱敏后可公开；
- `private`：只保存在本地，不进入公开作品集。

状态和范围不得用模糊措辞替代。

## 9. 发布与回溯

- 用户明确确认后才覆盖 `{identity-id}-作品集.md`；
- 发布后把平台、链接和更新时间写回 `{identity-id}-作品集.md`；
- 外部平台的版本历史作为默认回溯来源；
- 不生成 HTML、PDF、长图或其他本地导出；
- 不自动维护 `archive/`，也不复制素材到方向目录。

## 10. 交付前自检

- 30 秒内能否理解目标方向、主要案例和最强证据？
- 主案例是否承担不同证明任务？
- 每个主案例是否具备七项证据？
- 是否只展示最终界面，而没有关键判断和取舍？
- 项目状态、个人贡献和结果口径是否准确？
- 所有数字是否能从材料或公开证据回溯？
- 图片、视频、Demo 和源码是否可访问？
- 是否说明了每个媒体素材应重点看什么？
- 是否包含未脱敏的客户、内部系统、业务数据或账号？
- 作品集是否提供了简历之外的证据，而不是简历全文复述？
